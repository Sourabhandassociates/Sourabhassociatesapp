## Backend Architecture

Every module (`auth`, `clients`, `cases`, `tasks`, `documents`, `hearings`, `caseNotes`, `picklists`, `recycleBin`, `permissions`, `contacts`) follows the same three-layer shape:

```
*.routes.ts       — Express routing + middleware wiring (requireAuth, requireRole, rate limits, multer)
*.controller.ts   — thin HTTP adapter: parse the request (parseBody + req.params/req.actor), call the service, shape the response
*.service.ts      — business logic: Prisma calls, authorization checks (utils/authorization.ts), validation rules
```

Shared cross-cutting concerns live in `utils/` (`authorization.ts`, `errors.ts`, `validators.ts`, `securityLogger.ts`, `cookies.ts`, `jwt.ts`, `password.ts`, `idGenerator.ts`, `auditLog.ts`) and `middleware/` (`auth.ts`, `rbac.ts`, `rateLimit.ts`, `sanitize.ts`, `errorHandler.ts`) — a new module should reuse these rather than reinventing them, which is exactly the inconsistency this pattern was introduced to stop repeating (see ARCHITECTURE_REVIEW.md §2/§8 and CHANGELOG.md's "High: Consistency & Maintainability" entry).

### Standing Architectural Conventions

These were established during the Step 1 revision passes and are now the required pattern for all future work — the Managing Partner asked that they become permanent, not a one-off for the modules that introduced them:

- **Dropdowns are picklist-backed, never hardcoded.** Any field that would otherwise be a fixed `<select>` list (a status, category, type, or free-form-but-really-a-fixed-set value) must be added as a new `PicklistCategory` enum value (`backend/prisma/schema.prisma`) and rendered with `frontend/src/components/SearchableSelect.tsx`, not a hardcoded `<option>` list. One reusable `PicklistValue` table backs every category — `GET /api/picklists/:category` is open to any staff member, `POST`/`PATCH` are Managing-Partner-only (`backend/src/modules/picklists/`). This keeps spelling/terminology consistent everywhere the value is used (Global Search, Reports, and Tagging all benefit) and means the Managing Partner can add values without a code change. Business-logic-coupled enums (e.g., `TaskStatus`, `CaseStatus`, `DocumentConfidentiality` — values that drive actual code paths like badge colors or access rules, not just a curated list of labels) are the one exception and stay as Prisma enums.
- **Entity history is Audit-Log-derived, not a bespoke history table.** When a module needs a "who did what, when" trail (Task History is the reference implementation — `TASK_CREATED`/`TASK_REASSIGNED`/`TASK_STATUS_CHANGED` in `backend/src/modules/tasks/tasks.service.ts`), write to the existing generic `AuditLog` (`utils/auditLog.ts`'s `recordAuditLog`) rather than adding new columns or a new table. Read the trail back with `prisma.auditLog.findMany({ where: { entityType, entityId }, include: { user: {...} }, orderBy: { createdAt: "asc" } })` — this is the whole implementation, no new schema needed for a new entity to gain history.
- **A resource's primary detail screen is a single, professionally laid-out page — not a set of tabs the user must hunt across.** The Case Overview (`frontend/src/pages/Cases/CaseDetail.tsx`) is the reference pattern: grouped `Field`/definition-list sections (Case Identification, Litigation Team & Parties, Description) plus a dedicated Hearing Timeline sub-section, all visible without switching tabs. Future fields on an existing entity, and future entities that need their own detail screen (e.g., a Task Details screen — already built, `pages/Tasks/TaskDetail.tsx`), should follow this shape rather than scattering information across tabs by default.
- **Deletion is always soft, and reuses the same four-piece pattern.** A soft-deletable entity gets `deletedAt DateTime?` + `deletedById String?` + `deletedBy` relation + `@@index([deletedAt])` (see `Case`/`Client`/`Document`/`Task` in `backend/prisma/schema.prisma`); every existing list/get/search query for that entity adds `deletedAt: null`; a `DELETE /:id` route sets `deletedAt`/`deletedById` (never a real delete) and audit-logs it; and `backend/src/modules/recycleBin/recycleBin.service.ts` gets one new `case` branch per function (`listDeletedRecords`, `restoreRecord`, `permanentlyDeleteRecord`) plus the type name added to `RecyclableEntityType`. That switch-based-per-entity shape (rather than a single polymorphic Prisma query) is deliberate — Prisma's generated client gives every model its own distinctly-typed delegate, so true runtime genericity would require type-erasing to `any`, which this codebase's lint config forbids project-wide. Nothing else changes: the Recycle Bin UI, audit-log convention, and Managing-Partner-only gating are already generic across every entity that follows this shape.

## Security Posture

See [CHANGELOG.md](CHANGELOG.md) for the full history; this is the current-state summary.

- **Authentication:** JWT access tokens (15 min) + rotating opaque refresh tokens. The **Web Admin Portal** never receives its refresh token in a JSON body — it's set as an httpOnly, `SameSite` cookie (`backend/src/utils/cookies.ts`), invisible to JavaScript (including XSS). A future **mobile client** identifies itself with `X-Client-Platform: mobile` and receives the refresh token in the body instead, for storage in the platform's secure storage (Keychain/Keystore) — no header means "treat as web," the safer default.
- **Authorization:** every case/document/task/client endpoint is scoped server-side (`backend/src/utils/authorization.ts`) — never trust frontend routing/hiding alone. Out-of-scope resources 404, not 403, so existence isn't confirmed to an unauthorized caller. As of Step 3 M2, *which* action a role/user may take is resolved by the database-driven permission system (`middleware/permissions.ts`'s `requirePermission`, `modules/permissions/`) rather than hardcoded role lists; *which specific records* they may see stays exactly the same row-level scoping as before (`caseScopeWhere`/`clientScopeWhere`/`assertCaseAccess`/etc.), now selecting its filter tier via `resolveViewScope` instead of a hardcoded role array — the two systems are complementary, not overlapping, per STEP3_ROLE_PERMISSION_DESIGN.md §9.1.
- **Transport/headers:** Helmet's baseline header set, plus an explicit CORS origin allowlist (`CORS_ORIGIN` env var) instead of `*`.
- **Rate limiting:** `express-rate-limit` — a general ceiling across `/api`, and a tighter one on the login/refresh endpoints specifically. Disabled only under `NODE_ENV=test`.
- **File uploads:** MIME + extension allowlist, in-house magic-byte verification (catches a renamed/spoofed file that passes the allowlist check on its declared type alone), and a malware-scan integration point (currently a stub — no AV engine is provisioned).
- **Passwords:** staff passwords require 12+ characters with mixed case, a digit, and a symbol (`backend/src/utils/validators.ts`). Client passwords are system-generated (96 bits of entropy), not user-chosen, so complexity rules don't apply the same way.
- **Secrets:** `config/env.ts` refuses to start if `JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET`/`MFA_ENCRYPTION_KEY` (the last one added in Milestone 4, for AES-256-GCM-encrypting stored TOTP secrets) are under 32 characters. Generate one with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`.
- **Validation & sanitization:** every mutating endpoint validates its body through one shared `parseBody()` helper (`backend/src/utils/validators.ts`); a global middleware trims/strips-null-bytes from every JSON request body before any route-specific logic runs.
- **Security logging:** authentication failures, permission denials (role-based and row-level), rate-limit trips, and rejected file uploads are logged as structured JSON via `backend/src/utils/securityLogger.ts` — grep-able today, ready to ship to a real log aggregator later.

**Known limitations** (tracked in [TODO.md](TODO.md)): the malware-scan hook does real EICAR-signature + executable-magic-byte detection (Version 1.0 Milestone 4) but no full third-party AV engine (ClamAV daemon, cloud scanning API) is wired up yet; MFA is implemented (TOTP, Milestone 4) but as a post-login setup nudge for Managing Partner/Accounts Team rather than a hard pre-enrollment route block; CSRF is mitigated by design (Bearer-token auth on every state-changing endpoint, `SameSite` on the one cookie-authenticated endpoint) rather than a dedicated token scheme; `react-router-dom` and Vitest's dev-dependency chain carry known CVEs requiring breaking major-version upgrades, deliberately deferred to a dedicated Phase 8 pass (reassessed in Milestone 4 — no new advisories from the two new Milestone 4 dependencies); the Recycle Bin has no auto-purge after a retention period (SRD §27 lists this as optional) — deleted records stay recoverable indefinitely until a Managing Partner permanently deletes them; permanently-deleted Document files are removed from disk on a best-effort basis (no dead-letter/retry queue if the filesystem is unreachable at the moment of deletion, since the DB deletion itself must never be blocked or rolled back by a filesystem error).
