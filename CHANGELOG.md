## 2026-08-13 — Announcements Simplified, Firm Profile Trimmed, Sidebar Reordered

Three direct Managing Partner corrections delivered together, none requiring a schema migration.

**Office Announcements simplified to Title/Message only.** The v1.19 Priority/Audience/Start Date/Expiry Date fields are removed from the creation form and are no longer accepted by the API at all — `createSchema` in `announcements.controller.ts` shrinks to `{ title, body }`, and `createAnnouncement` in `announcements.service.ts` hardcodes `priority: "NORMAL"`, `audience: "EVERYONE"`, `startDate: null`, `expiryDate: null`, `selectedUserIds: []` rather than accepting a caller-supplied value for any of them — server-side enforcement, not just an emptied-out frontend form. Every announcement is therefore always visible to every active firm user and never to clients: `resolveRecipientUserIds("EVERYONE", [], actor.sub)` is now the only path taken, and this was already structurally guaranteed before this pass — `Notification.userId` only ever references `User`, never `Client`, and the client-portal page fetches nothing announcement-related. The v1.20 24-hour hard-ceiling auto-expiry required zero code changes: `isWithinDateWindow`'s `effectiveExpiry = min(expiryDate, createdAt + 24h)` already reduces to exactly `createdAt + 24h` once `expiryDate` is always `null`. `priority`/`audience`/`selectedUserIds`/`startDate`/`expiryDate` remain on the `Announcement` schema and on every announcement created before this pass — untouched, so history keeps displaying and auditing correctly. `Dashboard.tsx`'s composer drops the Priority/Audience selects, the selected-users checkbox picker, and the Start/Expiry date inputs down to just Title + Message + Post Announcement; priority badges are removed from both the moderation queue and the live-announcement cards. `AnnouncementDetail.tsx` drops its Audience/Starts/Expires display lines and priority badge, leaving Posted By and Date & Time. Dead CSS (`badge.priority-*`, `.announcement-card.priority-*`) removed from `index.css`.

**Firm Profile: GSTIN, SWIFT, and UPI ID removed.** GSTIN is no longer shown or editable in Firm Details (the firm does not use GSTIN for this invoice configuration); SWIFT and UPI ID are no longer shown or editable in Billing & Payment Settings. `firmProfile.service.ts`'s `DEFAULT_PROFILE` and `UpdateFirmProfileInput`, and `firmProfile.controller.ts`'s `updateSchema`, drop all three keys — since the Zod schema isn't `.strict()`, a caller that still sends `gstin`/`swift`/`upiId` has those keys silently stripped by `parseBody` rather than rejected, and they're never persisted going forward. The three `FirmProfile` schema columns are untouched, so any pre-existing values remain in the database, simply unread from this point on. `invoiceExport.pdf.ts`'s `FirmProfilePdfData` interface drops the three fields; the firm-detail header line drops its `GSTIN: ...` segment; the Payment Details section drops its `SWIFT: ...`/`UPI ID: ...` lines; `hasBankDetails` (which gates whether that section renders at all) drops the `|| firm.upiId` condition, now testing Bank Name/Account Number only. `FirmProfile.tsx`'s `DETAIL_ROWS`/`BANK_ROWS`/`BLANK_FORM`/`FormState` and edit-form JSX drop the same three fields. The QR-code "Scan to Pay" upload feature (a separate image, not the `upiId` text field) is completely untouched.

**Sidebar reordered.** `Layout.tsx`'s `NAV_ITEMS` array is reordered to a Managing-Partner-specified sequence — Dashboard, Clients, Contacts, Cases, My Tasks, Hearing Calendar, Cause List, Invoices, Firm Users, Role & Permissions, Employee Task Audit, Custom Fields, Firm Profile, Audit Log, Reports, Sessions, Admin Settings, Utilities, Recycle Bin, Security. Contacts and Utilities weren't named in the Managing Partner's 18-item ordering list (which only covered the other 18 modules); rather than drop either (the instruction was explicitly to rearrange, not remove), each was kept next to its closest logical neighbor — Contacts after Clients, Utilities after Admin Settings. This is a pure element-order change: the `roles`/`managingPartnerOnly` visibility-filtering logic (`visibleNavItems`) and the independent-scroll/slim-scrollbar sidebar CSS are both byte-for-byte unchanged.

**Testing:** `backend/tests/integration/announcements.test.ts` rewritten — tests targeting the now-removed audience-targeting (ASSOCIATE/SELECTED_USERS/ACCOUNTS_TEAM), priority, and explicit start/expiry-date behavior were replaced with a single test confirming those fields are silently ignored if a caller still sends them (every recipient still reached, audience/priority/dates always come back EVERYONE/NORMAL/null regardless of what was posted); the pre-existing 24-hour auto-expiry `isWithinDateWindow` unit tests and backdated-`createdAt` integration tests are unchanged, since the underlying function wasn't touched. `backend/tests/integration/adminCustomization.test.ts`'s Firm Profile tests updated to stop asserting a persisted GSTIN/UPI ID and instead assert `gstin`/`swift`/`upiId` stay `null` even when submitted. Full backend regression suite: **389/389 passing (37 files)**, zero regressions. Backend/frontend `tsc`/`eslint`/`build` all clean.

**Verification:** live browser walkthrough as a Managing Partner test account — created an announcement via the simplified two-field composer, confirmed it posted (201), reached other active firm users' notifications, and appeared on the Dashboard feed with no priority/audience/date UI anywhere; confirmed the Firm Profile screen shows Firm Details (Firm Name/Address/Phone/Email/Website/PAN, no GSTIN row) and Billing & Payment Settings (Bank Name/Account Holder Name/Account Number/IFSC/Branch/Payment QR Code, no SWIFT/UPI ID rows) with existing bank data intact; confirmed the sidebar renders in the exact requested order via the rendered accessibility tree.

## 2026-08-13 — Audit Log Expanded into a Complete Firm-Wide Audit Trail

Direct Managing Partner instruction: the Audit Log module (v1.10) had a working viewer screen but incomplete coverage underneath it — only a subset of modules called the write helper, several (auth/sessions/MFA, time logs) called it zero times, and updates only ever produced a hand-written free-text string, never a structured before/after. Requirement: every meaningful create/update/delete/permission-change/security/configuration action anywhere in the app must be audited, with a clear diff on updates, tamper-resistant, reliable via API as well as the frontend.

**Investigation first, per direct instruction.** A research pass across all ~20 service modules confirmed the write helper (`recordAuditLog`) and generic `AuditLog` table were sound as a foundation, but ~13 mutating functions never called it at all — most notably the entire `auth.service.ts` (login success/failure, logout, MFA enable/disable, session revoke, force-logout) and `timeLogs.service.ts` (create/update/delete), where a genuine hard-delete existed with zero audit trail.

**Two architectural forks, resolved directly with the Managing Partner before writing code.** (1) Coverage is completed via explicit `recordAuditLog(...)` calls at each gap — not a Prisma-extension/automatic-hook mechanism, which would have been this app's first generic ORM-level hook and a departure from its established "explicit, no hidden magic" convention (the same philosophy behind the Soft-Delete module's per-entity design). (2) The newly-audited security events are limited to discrete named account actions (login/logout/MFA/session-revoke/force-logout); `PERMISSION_DENIED`/`RATE_LIMIT_EXCEEDED` stay in the existing separate, unpersisted security logger — too high-frequency for a permanent business-audit table, and not state-changing actions.

**Schema.** `AuditLog` gains five additive, nullable columns: `userRole` (captured from the actor's JWT at write time — a later role change must never rewrite what a past action's role actually was), `entityName` (human-readable label for search/display — matter number, client ID, user name — instead of a bare truncated cuid), `changes` (`Json`/`jsonb`, a structured `{ field: { old, new } }` diff), `ipAddress`, `sessionId`; plus `@@index([action])`. One migration, zero-downtime (all nullable, no defaults needed).

**Central helper redesign (`utils/auditLog.ts`).** `recordAuditLog`'s trailing positional `details?: string` became an `options` object (`entityName?`, `details?`, `changes?`, `ipAddress?`, `sessionId?`) — every one of the ~64 existing call sites across 20 modules was updated in the same pass. A new `diffObjects(before, after, fields?)` compares two records field-by-field, normalizing `Date` values by instant rather than reference, applying a `SENSITIVE_FIELD_NAMES` blocklist (`passwordHash`, `mfaSecretEncrypted`, `mfaBackupCodesHashed`, `refreshTokenHash`) so a caller can safely diff a whole before/after record without hand-picking safe fields, and returning `null` — not an empty object — when nothing actually changed, so a no-op update produces no audit row at all rather than a row that says nothing happened.

**Automatic IP/session capture via AsyncLocalStorage (`utils/auditContext.ts`, new file).** One middleware in `app.ts` establishes a per-request context (`{ ip }`) before any router runs, including pre-auth routes like `/login` where the IP still matters; `middleware/auth.ts`'s `requireAuth` then mutates that same context with the verified session id the moment the token checks out. `recordAuditLog` reads this context automatically, so `ipAddress`/`sessionId` reach the database on every call without threading `req` through the ~40 service functions that needed new audit calls — the two-file wiring is the only place request context is touched at all.

**Coverage completion, module by module.** `cases.service.ts`: `createCase` (CASE_CREATED), `updateCase` (CASE_UPDATED, diffed, skipped on no-op), `setCaseStatus` (CASE_STATUS_CHANGED), `addAdvocate`/`removeAdvocate` (CASE_ADVOCATE_ADDED/REMOVED, by name). `clients.service.ts`: `updateClient` (CLIENT_UPDATED, diffed); `setClientStatus` gained an `actor` parameter it never had (CLIENT_STATUS_CHANGED). `tasks.service.ts`: `updateTask` gained a third, unconditional diff check for plain title/description/priority/dueDate edits (TASK_UPDATED) — deliberately excluding the fields already covered by the pre-existing reassignment/status-change branches, so a reassignment never also produces a redundant TASK_UPDATED row. `documents.service.ts`: `uploadDocument`/`addVersion` (DOCUMENT_UPLOADED/VERSION_ADDED — previously only delete was audited). `timeLogs.service.ts` (previously zero coverage): `createTimeLog`/`updateTimeLog`(diffed)/`deleteTimeLog` — the delete is a genuine hard-delete (unlike every other module's soft-delete), so its audit row is deliberately built to be meaningful standalone (hours, date, case), since it becomes the only surviving record the entry ever existed. `auth.controller.ts`: `createUser` (USER_CREATED), `setUserStatus` (USER_STATUS_CHANGED, diffed). `auth.service.ts` (the largest gap — previously zero coverage of the entire authentication surface): `AUTH_LOGIN_SUCCESS`/`AUTH_LOGIN_FAILURE` (staff login and the MFA-challenge step), `AUTH_MFA_ENABLED`/`AUTH_MFA_DISABLED`, `AUTH_LOGOUT` (`logout` gained an `actorId` param), `AUTH_FORCE_LOGOUT` (`forceLogoutUser` gained an `actor` param), `AUTH_SESSION_REVOKED`. `permissions.service.ts`/`picklists.service.ts`/`firmProfile.service.ts`/`contacts.service.ts`/`expenses.service.ts`/`hearings.service.ts`: existing free-text `details` calls were upgraded to also carry a structured `changes` diff where a real before/after existed (kept the original `details` string too, so no pre-existing test or Task-History rendering regressed).

**Read API / UI.** `auditLog.service.ts`'s `AuditLogFilters` gained `entityName` (case-insensitive contains). `AuditLogViewer.tsx`: the `startDate`/`endDate` and `userId` filters the backend already supported since v1.10 but the UI never surfaced are now exposed (user picker via the existing `/auth/staff-directory` endpoint, firm-wide actors only); a new `entityName` search input and column; a per-row expand/collapse revealing a Field/Previous Value/New Value table when `changes` is present. `TaskDetail.tsx`'s pre-existing history timeline renders the same `changes` as a compact inline "field: old → new" line for the new `TASK_UPDATED` entries, alongside the unchanged reassignment/status-change entries.

**Tamper-resistance.** Unchanged by design, not omission: `auditLogRouter` has only ever exposed `GET /` — no write route was ever built, and none is added. True database-role-level enforcement (`REVOKE UPDATE, DELETE`) was evaluated and explicitly deferred: the app's Postgres connection role owns the tables it created, and table owners bypass `REVOKE` in Postgres, so meaningful enforcement would require a separate least-privileged, non-owner role — an infrastructure change (connection-string/role split) out of scope for this pass, recorded as a known residual item rather than silently dropped.

**Deliberately not added, per "smallest reliable change" and direct verification against the live codebase.** Separate "Import Started"/"Import Failed" audit events — `parseAndValidate` (the preview step) mutates nothing, and `commitImport` either succeeds with a per-row created/skipped summary (already captured in the existing `DATA_IMPORT_COMPLETED` entry) or the whole commit throws, which isn't a distinct half-completed business state to audit. Invoice-delete and Payment-edit/reversal audit actions — no such mutating functions exist anywhere in the codebase; inventing them to have something to audit would have been new functionality, not a coverage pass.

**Testing:** new `backend/tests/integration/auditLog.test.ts` (structured-diff round-trip via the API, `entityName` filtering, no-op-update-skips-the-write, `diffObjects` redaction-blocklist and Date-normalization unit tests, `ipAddress`/`sessionId` auto-capture, tamper-resistance — `PATCH`/`PUT`/`DELETE` against `/api/audit-log` all 404). Extended `cases.test.ts`, `clients.test.ts`, `tasks.test.ts`, `auth.test.ts`, `mfaAndSessions.test.ts`, `timeLogsAndExpenses.test.ts` with assertions that the new coverage-completion call sites actually fire with correct `changes`/attribution, and that reassignment/status-change never double-fire alongside the new plain-field `TASK_UPDATED`. Seven pre-existing tests initially regressed when three modules' `details` strings were replaced outright by `changes` objects (`CASE_REASSIGNED`, `ROLE_PERMISSION_CHANGED`, `TASK_REASSIGNED`) — fixed by restoring the original `details` string alongside the new `changes` field in all three, so no existing assertion (or the Task History timeline's rendering, which still reads `details` for those two action types) lost information. Full backend regression suite: **393/393 passing (37 files)**, zero regressions (up from 369/369 pre-change — the +24 are new/extended audit-trail tests).

**Verification:** backend/frontend `tsc`/`eslint`/`build` all clean. Live browser walkthrough as a fresh Managing Partner test account: edited a Case's Practice Area through the UI and confirmed a `CASE_UPDATED` row with an expandable `practiceArea: — → Real Estate Litigation` diff table; edited the Firm Profile's Bank Name and confirmed `FIRM_PROFILE_UPDATED` showed `bankName: IDFC FIRST BANK → New Test Bank Ltd` — matching the Managing Partner's own example format exactly; confirmed `AUTH_LOGIN_SUCCESS` appeared for that same login; called `PATCH /api/tasks/:id` **directly via `fetch`, bypassing the frontend UI entirely**, and confirmed the resulting `TASK_UPDATED` entry appeared correctly in the Task Detail history timeline — proving the audit trail is reliable for API-only clients, not just UI-driven actions; logged in as a separate Associate test account (holding neither `AUDIT_LOG.VIEW_ALL` nor `VIEW_OWN`) and confirmed `GET /api/audit-log` returned 403 both times it was called. Test accounts deactivated and test data (Practice Area, Bank Name, Task title/description) reverted afterward.

**Files:** `backend/prisma/schema.prisma` (+1 migration), `backend/src/utils/auditLog.ts`, `backend/src/utils/auditContext.ts` (new), `backend/src/app.ts`, `backend/src/middleware/auth.ts`, `backend/src/utils/authorization.ts` (widened two `select`s to carry fields the new diffs/entityNames need), `backend/src/modules/{auth,cases,clients,tasks,documents,timeLogs,contacts,expenses,firmProfile,hearings,permissions,picklists,recycleBin,customFields,announcements,dataImport,invoices,caseNotes}/*.service.ts`, `backend/src/modules/auth/auth.controller.ts`, `backend/src/modules/clients/clients.controller.ts`, `backend/src/modules/auditLog/auditLog.service.ts` + `auditLog.controller.ts`, `backend/tests/integration/auditLog.test.ts` (new) + 6 extended test files, `frontend/src/pages/Admin/AuditLogViewer.tsx`, `frontend/src/pages/Tasks/TaskDetail.tsx`, `frontend/src/index.css`, `docs/SRD_v1.21.md` (new).

## 2026-08-12 — Office Announcements: 24-Hour Hard-Ceiling Dashboard Auto-Expiry

Direct Managing Partner instruction, same day as the internal-communication-system enhancement above: an announcement should automatically disappear from the Dashboard exactly 24 hours after it was posted — server-side, so it stays hidden across refreshes, other devices, and logout/login, with no manual "Archive" action required and no data permanently deleted.

**One genuine fork, resolved by asking directly.** Should the 24-hour rule be a hard ceiling applying even over a longer explicit Expiry Date, or only a default when no Expiry Date is set? Asked rather than guessed: the Managing Partner confirmed a **hard ceiling for every announcement** — an explicit Expiry Date can only narrow the window, never extend it past 24 hours.

**Backend — one function, evaluated live.** `announcements.service.ts` gains `isWithinDateWindow(now, createdAt, startDate, expiryDate)`, computing `effectiveExpiry = min(explicit expiryDate, createdAt + 24h)`. `listAnnouncements()`'s existing filter and `isEffectivelyActive` computation now both pass `a.createdAt` through it, so the 24-hour ceiling applies wherever the date window was already being checked, with no new call site. Consistent with this deployment having no job-scheduler infrastructure (documented in the v1.19 write-up above), nothing is physically flipped at the 24-hour boundary — every read simply recomputes whether "now" falls inside the window. The ceiling is measured from the announcement's original `createdAt`, confirmed to hold even for an Office-Staff draft published later by the Managing Partner (the draft's `createdAt` predates its publish time, and the ceiling uses that original timestamp, not the publish moment).

**Deliberately unchanged, to honor "audit/history remains available."** `getAnnouncementById` and `getAnnouncementReadTracking` are untouched — a recipient who already holds a Notification row for an expired announcement, or the Managing Partner doing oversight, can still open its full detail and Read Tracking panel directly. No new "Expired Announcements" browsing screen was built, since the existing detail-access path already satisfies the requirement without exceeding the requested "smallest reliable change." No schema, migration, controller, route, or frontend file was touched — this is a single-function, single-file backend change.

**Testing:** 6 new tests in `announcements.test.ts` — `isWithinDateWindow` unit tests (just-under/just-over the 24h boundary, an explicit Expiry Date beyond 24h capped rather than extended, an explicit Expiry Date sooner than 24h still narrowing as before) plus integration tests backdating an announcement's `createdAt` via direct Prisma `update()` to prove the ceiling holds for a non-Managing-Partner's Dashboard list while the Managing Partner still sees it (with `isEffectivelyActive: false`) for moderation, and that publishing a backdated Office-Staff draft doesn't reset the ceiling. Full backend regression suite: **369/369 passing (36 files)**, zero regressions.

**Verification:** backend `tsc`/`eslint` clean (2 pre-existing, unrelated warnings only); frontend `tsc`/`eslint`/`build` unaffected (no frontend file touched). Live browser walkthrough: posted a fresh announcement as a test Managing Partner account, confirmed it displayed immediately in the Dashboard's active section; backdated its `createdAt` to 25 hours ago via a direct Prisma script; reloaded and confirmed it no longer appeared in the poster's own Dashboard feed; navigated directly to its detail URL and confirmed Title/Message/Posted By/Date & Time and a full Read Tracking panel (7 recipients, 0 read) remained fully intact, proving the data was hidden, not deleted; logged in as a separate Associate account and confirmed the same exclusion held there too, proving the filter is server-side and account-independent, not a client-side artifact of the posting session. Test accounts deactivated afterward via `/users`.

**Files:** `backend/src/modules/announcements/announcements.service.ts`, `backend/tests/integration/announcements.test.ts`, `docs/SRD_v1.20.md` (new).

## 2026-08-12 — Office Announcements Enhanced into a Full Internal-Communication System

Direct Managing Partner instruction: turn the existing (fairly minimal) Office Announcements Composer into a reliable in-app communication channel — automatic notifications, priority levels, audience targeting, an expiry window, and per-recipient read tracking — so important information stops depending on someone happening to scroll past the Dashboard widget.

**One genuine fork, resolved by asking directly.** The requested Audience list included both "Managing Partners" and "Partners" as separate options, but this app's role model has only `MANAGING_PARTNER` — there is no distinct "Partner" tier below it (Associates/Junior Associates are the fee-earners). Asked rather than guessed: the Managing Partner confirmed dropping "Partners" entirely rather than aliasing it to a duplicate menu entry pointing at the same role.

**Schema.** `Notification.readAt` (nullable `DateTime`) records when `isRead` flips true — a small, generically useful addition (not announcement-specific) that lets Read Tracking show a per-user timestamp instead of just a boolean. `Announcement` gains `priority` (`AnnouncementPriority`: NORMAL/IMPORTANT/CRITICAL), `audience` (`AnnouncementAudience`: EVERYONE/MANAGING_PARTNER/ASSOCIATE/OFFICE_STAFF/ACCOUNTS_TEAM/SELECTED_USERS), `startDate`/`expiryDate` (both optional `DateTime`), and `selectedUserIds` (`String[]`) — the last one caught a real design bug during implementation: without persisting the admin's Selected-Users choice on the announcement itself, an Office-Staff-authored draft would silently lose that selection by the time a Managing Partner later published it, since a draft creates no `Notification` rows at all until publish. Two migrations (the enum/date-window/readAt columns, then the follow-up `selectedUserIds` column added after the first was already applied to both databases and could no longer be edited in place).

**Backend — notification fan-out reuses the existing `Notification` table rather than inventing a parallel one.** `announcements.service.ts`'s `resolveRecipientUserIds` resolves an audience selection to concrete active-user ids (ASSOCIATE targets both ASSOCIATE and JUNIOR_ASSOCIATE, matching the SRD's own "Advocates" grouping), excluding the poster. `createAnnouncement` fans out one `notify()` call per recipient immediately for a live (Managing-Partner-authored) announcement, but skips it entirely for an Office-Staff draft — `setAnnouncementActive` fires the fan-out itself at the moment a draft is actually published, using the persisted `selectedUserIds`/`audience` rather than re-deriving them. Those `Notification` rows *are* the recipient list from then on: `getAnnouncementReadTracking` (Managing-Partner-only, 403 for anyone else) just queries them (entityType `"Announcement"`, matching entityId) and splits by `isRead` — no separate recipient-snapshot table needed. `getAnnouncementById` scopes access the same way every other row-scoped screen in this app does: the Managing Partner can open anything (oversight), everyone else only an announcement they actually hold a Notification row for, 404 otherwise, so guessing another announcement's id can't leak content meant for a narrower audience. `markAnnouncementRead` marks that same row read+timestamped, a no-op (not an error) if the actor was never a recipient. `listAnnouncements` filters non-Managing-Partner viewers to announcements currently inside their date window (`isWithinDateWindow`, a pure read-time check — no background scheduler exists anywhere in this app, so nothing physically flips a flag at the boundary); the Managing Partner still sees everything, with a computed `isEffectivelyActive` flag telling them what's currently live.

**Frontend.** `NotificationBell.tsx` now navigates to a new `/announcements/:id` on click for an Announcement-type notification (every other notification type keeps its existing mark-read-in-place behavior, unchanged — out of scope for this pass). New `AnnouncementDetail.tsx`: Title/Message/Posted By/Date & Time, auto-marks the viewer's notification read on open, a "Mark as Read" fallback for the explicit-without-opening path, and — Managing-Partner-only — a Read Tracking panel (total/read/unread counts, a read list with per-user timestamp, an unread list). `Dashboard.tsx`'s Announcements widget composer gained Priority/Audience selects, a Selected-Users checkbox picker (`/auth/staff-directory`, the same lightweight roster used elsewhere), and Start/Expiry date inputs; each announcement card shows a priority badge, an "Unread" badge and inline "Mark as Read" for the viewer's own read state, and now links through to the detail screen; the "active" feed filters on the new `isEffectivelyActive` flag instead of the raw `isActive` boolean.

**Testing:** 11 new integration tests (audience resolution per type including Selected-Users validation, draft-vs-published notification timing, GET/read/read-tracking authorization, date-window filtering both directions, priority persistence) plus the five pre-existing announcement tests left untouched and still passing; full backend regression suite 363/363 passing (36 files), zero regressions.

**Verification:** backend/frontend `tsc`/`eslint`/build all clean. Live browser walkthrough across three roles: posted a Critical/Everyone announcement as the Managing Partner; confirmed the bell showed it with a `[Critical]`-prefixed message for a separate Associate account, clicking it navigated to the detail screen and auto-marked it read; confirmed the Managing Partner's Read Tracking panel then showed 1 read (with timestamp) and the other 7 recipients unread; separately posted a Selected-Users announcement with an expiry date and confirmed the read-tracking recipient count matched the single selected user. Test accounts and announcements created during verification were archived/deactivated afterward.

**Files:** `backend/prisma/schema.prisma` (+2 migrations), `backend/src/modules/announcements/{announcements.service,announcements.controller,announcements.routes}.ts`, `backend/src/modules/notifications/notifications.service.ts`, `backend/tests/integration/announcements.test.ts` (new), `frontend/src/components/NotificationBell.tsx`, `frontend/src/pages/Announcements/AnnouncementDetail.tsx` (new), `frontend/src/pages/Dashboard.tsx`, `frontend/src/App.tsx`, `frontend/src/index.css`, `docs/SRD_v1.19.md` (new).

## 2026-08-12 — Data Import Relocated to Admin Settings → Utilities

Direct Managing Partner instruction: Data Import isn't a daily operational feature for a law firm, so it shouldn't sit in the main sidebar alongside Cases/Clients/Tasks. Requirement: remove it from the top-level sidebar, create a new "Utilities" section under Admin Settings, and move Data Import (plus, per the original list, Data Export/Backup/Restore) into it — visible only to users with the appropriate administrative permission, with every existing route/permission/bookmark still working.

**Scope check before touching anything.** Only Data Import exists as its own screen. "Data Export" isn't a separate feature — export is served by the Reports screen's own PDF/Excel pipeline (including a Client List report type). "Backup" and "Restore" (database-level) don't exist anywhere in the app at all; the Recycle Bin's per-record restore is a completely different feature. Asked directly rather than inventing placeholder tiles for functionality that was never built (which would have quietly violated the "do not change any functionality" instruction by implying capabilities that don't exist): the Managing Partner confirmed moving only Data Import.

**Frontend.** New `Admin/Utilities.tsx` — a landing page under Admin Settings (`/admin/utilities`) listing one-time/occasional admin tools as cards; today, just Data Import. Data Import itself moves from `/data-import` to `/admin/utilities/data-import` (`DataImport.tsx`'s own code is untouched beyond adding a breadcrumb). A new shared `Breadcrumbs.tsx` component (the first breadcrumb trail anywhere in this app, needed now that a screen sits two levels deep) renders "Admin Settings / Utilities / Data Import" on the Data Import page and "Admin Settings / Utilities" on the hub. `Layout.tsx`'s sidebar drops the "Data Import" entry and gains a "Utilities" entry in its place, gated by the exact same roles Data Import always had (`["MANAGING_PARTNER", "OFFICE_STAFF"]`, matching `DATA_IMPORT.RUN`'s permission default) — so nobody gains or loses access, only the entry point's label and destination change.

**Backward compatibility.** `App.tsx` keeps a route at the old `/data-import` path that immediately redirects (`<Navigate replace>`) to `/admin/utilities/data-import`, so any existing bookmark, deep link, or browser-history entry still lands on the right page. ## 2026-08-06 — Pre-Deployment Billing Bug Fix + Payment-Status Completion

Reported by the Managing Partner ahead of deployment: "not able to create a new invoice." Investigated the full invoice creation flow end-to-end (frontend form → API route → validation → permissions → service → DB) before touching any code, per the Managing Partner's explicit instruction.

**Root cause (frontend-only, no backend defect):** `CaseBilling.tsx`'s `CreateInvoiceSection` returned `null` — the entire "Create Draft Invoice" card, not just a disabled button — whenever a case had zero unbilled time logs *and* zero unbilled expenses. The backend has always accepted free-form `manualItems` (arbitrary description/quantity/rate lines) for exactly this scenario — a fixed-fee or retainer invoice, or billing before any time/expense is logged — but the UI never exposed a way to add one, so a case with nothing yet logged had no invoice-creation path in the product at all. Confirmed via the automated `invoices.test.ts` suite (which already exercised the API directly and passed) and via a live browser reproduction against a case with no time/expense entries, which showed the entire card missing.

**Fix:** the card now always renders (as long as the case has a linked client), with the existing unbilled-time/unbilled-expense pickers plus a new manual-line-item builder (add/remove description+quantity+rate rows). A case with no linked client shows an explanatory message instead of silently disabling the submit button. Also added a due-date input to invoice creation — previously absent from the UI entirely (the backend's `dueDate` field was always sent as `undefined`), which meant the SRD's "overdue alerts" line could never have triggered for any invoice created through the product, a second latent defect against the same feature.

**New: payment-status tracking** (completes SRD §16.1's "payment tracking ... due dates, overdue alerts," previously only partially delivered in Milestone 2) — a derived `paymentStatus` (`PENDING`/`PARTIALLY_PAID`/`PAID`/`OVERDUE`), distinct from `Invoice.status`'s DRAFT→APPROVED→SENT→PARTIALLY_PAID→PAID lifecycle. `PAID` takes priority; otherwise `OVERDUE` once the due date has passed; otherwise `PARTIALLY_PAID` if a partial payment exists; otherwise `PENDING`. Computed on read (`invoices.service.ts`'s `derivePaymentStatus`/`withPaymentStatus`), not stored or cron-driven — the same pattern already used for Task `OVERDUE`. Applied to every invoice-returning endpoint (`POST /api/invoices`, `GET /api/invoices`, `GET /api/invoices/:id`, `PATCH .../approve`, `PATCH .../send`) via one shared function, so all four UI surfaces reading it can never drift out of sync.

**Frontend:** payment-status filter tabs (All/Pending/Partially Paid/Fully Paid/Overdue) plus a new invoice-number/matter/client search box on the Invoice List (`/invoices`), both combining via AND with the existing lifecycle-status dropdown; a color-coded payment-status badge (green/amber/red/neutral, reusing the existing `.badge.status-*` CSS convention) on the Invoice List, Invoice Detail, the Case Billing tab's invoice list, and the Dashboard's Accounts Team "Outstanding Invoices" widget, which also gained a dedicated Overdue-count stat tile and now derives "outstanding" from `paymentStatus` instead of re-deriving it locally.

**Real second bug caught by a new test, before commit:** `createDraftInvoice`'s own response was missing the new `paymentStatus` field (`withPaymentStatus` had only been wired into `listInvoices`/`getInvoice`, not the create/approve/send paths) — a test asserting `paymentStatus` on the create response failed immediately, exposing the gap. Fixed by wiring `withPaymentStatus` into `createDraftInvoice`, `approveInvoice`, and `sendInvoice` as well.

**Testing:** 5 new tests in `invoices.test.ts` (manual-line-item-only invoice creation, still-rejects-truly-empty-invoice, `PENDING`/`OVERDUE` derivation including PAID-always-wins, and payment-status query filtering combined with the existing status filter) plus `paymentStatus` assertions added to the existing Pending→Partially-Paid→Paid transition test. Full backend regression suite re-run, zero regressions.

**Verification:** backend/frontend `tsc`/`eslint` clean; live browser walkthrough — created an invoice via manual line item on a case with zero logged time/expenses (reproducing and then confirming the fix for the reported bug), verified the payment-status badge and filter tabs, verified a partial-then-full payment sequence transitions the badge Pending → Partially Paid → Paid, and verified an overdue invoice (past due date, unpaid) shows the Overdue badge/filter/dashboard tile correctly.

## 2026-08-04 — Step 3 M3: Permission-Management Admin API

Third milestone for Step 3, built exactly per STEP3_ROLE_PERMISSION_DESIGN.md §6/§11: the Managing-Partner-only backend surface that will power the M4 admin UI, and the first place Rule A/Rule B (built in M2, unit-tested in isolation) get wired into a live mutation path.

**New module** (`backend/src/modules/permissions/{permissions.service,permissions.controller,permissions.routes}.ts`, mounted at `/api/permissions`): every route gated by `USERS.MANAGE_PERMISSIONS` **and** a hardcoded `requireRole("MANAGING_PARTNER")` safety net that stays in place regardless of what the configurable system says (design doc §9.2 — the one screen that controls every other permission can't have its own access depend entirely on the system it configures).

- **`GET /catalogue`, `GET /role-defaults`** — the full permission catalogue and the dense RolePermission matrix, for the Role Defaults screen to render.
- **`PATCH /role-defaults`** — bulk role-default edit. Every change in a batch is validated (unknown role, unknown permission key, Rule A) *before* any write is attempted, so an invalid entry anywhere in the batch rejects the whole batch, nothing partial. Only changes that actually flip a value are written and audit-logged as `ROLE_PERMISSION_CHANGED`; a resubmission of an already-current value is a silent no-op, matching the existing convention that audit entries record real transitions, not attempted-but-unchanged requests (same pattern as Task reassignment logging). **Rule A is enforced here for the first time on a live route**: revoking a core-admin permission from the Managing Partner role default is rejected unconditionally.
- **`GET /employees/:userId`** — Permission Summary: role, every role-default permission, every override, and the merged effective grant, each entry explicitly tagged `source: "role-default" | "override"` so inherited vs. overridden never has to be inferred by the caller. One payload backs both the Permission Summary screen and the Employee Overrides tab's "view effective permissions" requirement.
- **`POST /employees/:userId/overrides`** — grants or revokes an individual override. Reason is mandatory (400 if blank), the permission key must exist (400 if not), and a duplicate override for the same employee/permission is rejected with 409 rather than silently upserted — matching the Employee Overrides UI's own shape (an existing-override row offers Remove, not a second Grant). **Rule B is enforced here for the first time on a live route**: a `REVOKE` override on a core-admin permission targeting a Managing-Partner-role employee is rejected unconditionally.
- **`DELETE /employees/:userId/overrides/:permissionKey`** — removes a single override, reverting that one permission to the role default on the very next request (audit-logged `USER_PERMISSION_OVERRIDE_REMOVED`).
- **`POST /employees/:userId/reset`** — bulk-removes every override for an employee in one action, writing a single `USER_PERMISSIONS_RESET` audit entry (not N individual removals); a no-op (zero overrides) writes no entry at all.

**Managing Partner Safety extended to account deactivation:** `PATCH /api/auth/users/:userId/status` (predates Step 3) now rejects deactivating the sole active Managing Partner — added in place, following that file's existing pattern of keeping business logic directly in the controller rather than introducing a new service layer for one check (`auth.controller.ts` already mixes controller/service responsibilities for its admin actions; M3 follows the file's established convention rather than "fixing" unrelated code, per the Managing Partner's explicit "do not modify unrelated functionality" instruction).

## 2026-08-03 — Step 2: Soft Delete & Recycle Bin (SRD Version 1.4)

The Managing Partner approved Step 1's second revision and requested Step 2 exactly as specified in SRD §27, with 8 explicit requirements: soft delete for Case/Client/Document/Task; no normal-user action ever permanently deletes a record; deleted records move to a Recycle Bin; only the Managing Partner can view/restore/permanently-delete from it; every delete/restore/permanent-delete is audit-logged; deleted records never appear in normal searches/dashboards/reports; restore brings back the complete record with relationships intact; and the architecture is generic enough for future modules to reuse. All 8 are implemented. 137 backend tests pass (121 pre-existing + 16 new), zero regressions; both packages type-check, lint, and build cleanly; every feature verified live in the browser (soft-delete → disappears from list → appears in Recycle Bin → restore → reappears with relationships intact, confirmed end-to-end for a Case).

**1. Schema.** `Case`, `Client`, `Document`, and `Task` each gained `deletedAt DateTime?`, `deletedById String?`, and a `deletedBy` relation to `User` (plus `@@index([deletedAt])`) — migration `20260803120027_step2_soft_delete_recycle_bin`. A null `deletedAt` means "not deleted"; no separate boolean flag is needed. The same migration adds `onDelete: Cascade` to every child relation of these four entities that didn't already have a referential action specified (`CaseClient`, `CaseAdvocate`, `Document.case`, `DocumentVersion.document`, `Task.case`, `CaseNote.case`, `Hearing.case`, `ClientSession.client`) so permanent deletion cascades correctly at the database level — this also resolves ARCHITECTURE_REVIEW.md §1's previously-flagged gap ("No onDelete/onUpdate referential actions specified anywhere").

**2. Excluding soft-deleted records everywhere.** Every existing list/get/search query across `cases`, `clients`, `documents`, `tasks`, and `hearings` services now filters `deletedAt: null` (including cross-cutting cases like a task or hearing whose *parent case* is soft-deleted, even if the task/hearing row itself isn't). The shared row-level authorization helpers (`assertCaseAccess`, `assertDocumentAccess`, `assertTaskAccess`, `assertClientAccess` in `utils/authorization.ts`) all now 404 on a soft-deleted record — indistinguishable from a record the caller was never authorized to see. Client login (`auth.service.ts`) treats a soft-deleted Client identically to a non-existent one.

**3. Soft-delete trigger endpoints.** New `DELETE /:id` on each of `cases`, `clients`, `documents`, `tasks` — never a real delete, always sets `deletedAt`/`deletedById` and audit-logs `{ENTITY}_DELETED`. Role gates mirror each entity's existing highest-privilege mutation role: Case/Document/Task allow Managing Partner or Associate; Client is Managing-Partner-only (matching the existing `setClientStatus` pattern).

**4. Recycle Bin module (new, Managing-Partner-only).** `backend/src/modules/recycleBin/` — `GET /api/recycle-bin` lists every soft-deleted record across all four types with a human-readable label and who/when it was deleted; `POST /:entityType/:id/restore` clears `deletedAt`/`deletedById` (audit-logged `{ENTITY}_RESTORED`); `DELETE /:entityType/:id` permanently deletes via `prisma.{model}.delete` — which cascades to dependent rows through the new schema-level `onDelete: Cascade` relations — and audit-logs `{ENTITY}_PERMANENTLY_DELETED`. Permanent delete requires the record to already be soft-deleted; **even the Managing Partner cannot skip the soft-delete step**. Permanently deleting a Document also best-effort-removes each version's file from disk (`fs.unlink`, wrapped in try/catch per file, run only after the DB delete succeeds, so a missing/inaccessible file never blocks or rolls back the already-successful deletion). **Design decision — "generic" interpreted as one shared module with a switch over entity type**, not a fully polymorphic Prisma wrapper: Prisma's generated client gives each model its own distinctly-typed delegate, so true runtime genericity would require type-erasing to `any`, forbidden by this codebase's `@typescript-eslint/no-explicit-any: error` lint rule. Adding a fifth soft-deletable entity later means adding the schema columns, one `case` branch per function in `recycleBin.service.ts`, and one union member to `RecyclableEntityType` — documented in both SRD §27 (v1.4) and README.md's "Standing Architectural Conventions."

**5. Frontend.** "Delete Case"/"Delete Client" buttons on their respective detail screens (role-gated to match the backend), and a Delete column on the Documents and Tasks tabs of the Case Overview (`CaseDetail.tsx`), each behind a `window.confirm`. New `pages/Admin/RecycleBin.tsx` (route `/admin/recycle-bin`, nav-linked for Managing Partner only) lists every deleted record with Restore / Permanently Delete actions, the latter behind a stronger confirmation warning ("cannot be undone").

**6. Tests.** New `backend/tests/integration/recycleBin.test.ts` (16 tests): soft-delete visibility/row-scoping for each of the four entities (including a Task disappearing from My Tasks, the firm-wide list, and the Employee Task Audit simultaneously), Recycle Bin listing/restore/permanent-delete all rejected for non-Managing-Partner callers, restore verified to bring back relationships intact and to 404 on a non-deleted record, permanent-delete verified to 404 on a never-soft-deleted record (proving the no-bypass rule), cascade-on-permanent-delete verified via direct `prisma.{model}.findUnique` returning `null` post-delete for a Case's Tasks/Documents/DocumentVersions, and an unknown entity type returning 400.

**7. Documentation.** SRD bumped to **Version 1.4** (`docs/SRD_v1.3.md` marked superseded) — Section 27 amended with the concrete field names (`deletedAt`/`deletedById` in place of the generic `is_deleted`/`deleted_at`/`deleted_by` naming) and the generic-architecture design decision. ## 2026-08-02 — High: Security Hardening

Implements IMPROVEMENTS.md items 5–11, at the Managing Partner's explicit direction to prioritize security/confidentiality/data-integrity over convenience given this handles confidential legal information. No functionality removed; 85 automated tests pass (up from 75).

**Headers, CORS, rate limiting:**
- `helmet()` added to `app.ts` (with `crossOriginResourcePolicy: cross-origin`, since the API is deliberately called cross-origin by the SPA).
- CORS locked to an explicit origin allowlist (`CORS_ORIGIN` env var, defaults to `http://localhost:5173`) with `credentials: true`, replacing the previous open `cors()`.
- `express-rate-limit`: a general ceiling across `/api` (300 req/15min) and a tighter one on `login/staff`, `login/client`, and `refresh` (10 req/15min) — `backend/src/middleware/rateLimit.ts`. Disabled only under `NODE_ENV=test` (the automated suite's rapid repeated requests are the point, not abuse). Trips are logged via the new security logger.

**Refresh-token storage — cookie-based for web, JSON-body preserved for mobile:**
- New `backend/src/utils/cookies.ts`: the Web Admin Portal's refresh token is now set as an httpOnly, `SameSite` cookie (`saa_refresh_token`, scoped to `/api/auth`) and is **never present in a JSON response body**. A future mobile client identifies itself with `X-Client-Platform: mobile` and continues receiving the refresh token in the body (no header = treated as web, the safer default).
- `auth.controller.ts`'s `staffLogin`/`clientLogin`/`refresh` branch on this; `logout` now also clears the cookie.
- Frontend (`api/client.ts`, `authStorage.ts`, `AuthContext.tsx`): `withCredentials: true` added to the axios instance; `refreshToken` removed entirely from `localStorage`/`AuthState` — only the short-lived access token and non-sensitive session metadata are kept there now.

**File upload validation:**
- `storage.ts`: Multer `fileFilter` now allowlists extension + declared-MIME-type combinations (PDF, DOC, DOCX, JPG, PNG, TIFF) instead of accepting anything.
- New `documents/fileValidation.ts`: post-upload magic-byte verification (written in-house — the maintained third-party option, `file-type` 21+, is pure-ESM and this project's CommonJS TypeScript build can't resolve its types without a much broader, riskier module-resolution change) catches a file whose actual content doesn't match its declared type (e.g., a script renamed to `.pdf`). Also the designated malware-scan integration point (`scanForMalware` — currently a pass-through stub; no AV engine is provisioned).
- `errorHandler.ts`: Multer's own errors (e.g., file-too-large) are now mapped to a proper 400 instead of falling through to a raw 500.

**Password policy & secrets:**
- `utils/validators.ts`'s `passwordSchema`: staff passwords now require 12+ characters, upper+lowercase, a digit, and a symbol. Client temporary-password entropy bumped from 48 to 96 bits.
- `config/env.ts`: `JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET` must be ≥32 characters or the app refuses to start. Dev/test secrets regenerated accordingly.

**Centralized validation, sanitization, security logging:**
- New `utils/validators.ts`'s `parseBody()`: every controller (auth, clients, cases, tasks, documents) now validates its body through this one function instead of a hand-rolled `safeParse` + throw in each handler.
- New `middleware/sanitize.ts`: a global middleware trims strings and strips null bytes from every JSON request body before route-specific validation runs.
- New `utils/securityLogger.ts`: structured JSON logging for login failures, disabled-account attempts, permission denials (both role-based `403`s and row-level-scoped `404`s where the resource actually exists), rate-limit trips, and rejected file uploads.

**CSRF:** not mitigated via a dedicated token scheme — a reasoned decision, not an oversight. Every state-changing endpoint authenticates via a Bearer token in the `Authorization` header (unforgeable by a cross-site request); the one cookie-authenticated endpoint (`/api/auth/refresh`) relies on `SameSite` as its mitigation.

**Testing:** 10 new tests — `tests/integration/cookieAuth.test.ts` (web vs. mobile token delivery, refresh rotation, logout clearing the cookie), `tests/integration/securityHeaders.test.ts` (Helmet headers, CORS allow/deny), `tests/unit/rateLimit.test.ts` (isolated 429 behavior), plus 5 file-upload-validation tests added to `tests/integration/documents.test.ts`.

**Also fixed in passing:** a latent bug where a large file upload produced a raw 500 instead of a 400 (Multer's own error class wasn't recognized by the error handler).
