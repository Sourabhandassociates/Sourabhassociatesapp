## Known Issues / Gaps in What's Already Built (Phase 1)

These exist in the current codebase and should be addressed before this goes anywhere beyond local development:

1. ~~Seeded Managing Partner password is a placeholder~~ Still true (`partner@saa.local` / `ChangeMe123!`) — change it (or re-seed with a real password) before any shared/hosted use. Not addressed by Security Hardening since it's a data/ops step, not a code fix.
2. ~~JWT secrets and DB password in `backend/.env` are dev placeholders~~ **Fixed:** `config/env.ts` now rejects any secret under 32 characters at startup (`requireStrongSecret`), and the dev/test `.env`/`.env.test` files were regenerated with strong random values. The DB password itself is still a local dev convenience value — rotate it before any shared/hosted use.
3. ~~CORS is wide open~~ **Fixed:** `cors()` now takes an explicit origin allowlist from `CORS_ORIGIN` (defaults to `http://localhost:5173`), with `credentials: true` for the refresh-token cookie.
4. **`react-router-dom` has known moderate CVEs** at the currently pinned version (open-redirect related). The fix requires a breaking major-version upgrade — deferred intentionally to Phase 8 (Security Hardening infra pass) rather than done silently.
4b. **`vitest`'s dev-dependency chain (`vite`/`esbuild`) has known moderate/high/critical advisories**, same category as #4 — all require a running dev/UI server exposed to an untrusted network to be exploitable (e.g., `vitest --ui`), which this project never does (`npm test` runs `vitest run`, one-shot, no server). Fixing requires a breaking major-version bump (vitest 2.x → 4.x); deferred to Phase 8 alongside #4 rather than force-upgraded mid-hardening-pass. **Constraint: never run `vitest --ui` against this codebase until this is resolved.**
5. ~~Office Staff case visibility isn't field-redacted.~~ **Addressed in Version 1.0 Milestone 4:** `Case.description` (case-strategy free text) is redacted to `null` for Office Staff on both `listCases` and `getCase`, at the response layer.
6. ~~No automated test suite~~ **Addressed for authorization:** 85 automated tests (`backend/tests/`, run via `npm test`) cover role-gating, row-level scoping, and now also security headers, rate limiting, cookie-based auth, and file-upload validation. Still missing: broader functional/business-logic test coverage beyond security (e.g., Matter Number/Client ID sequencing under concurrency, document versioning edge cases), and no frontend test coverage at all.
7. ~~No pagination~~ **Addressed in Version 1.0 Milestone 4:** Cases, Clients, Case Documents, and Case Tasks list endpoints now accept `page`/`pageSize` and return `X-Total-Count`/`X-Page`/`X-Page-Size` headers (body stays a plain array for backward compatibility).
8. **No case status-transition validation** — a case can currently jump between any two statuses; no enforcement of a sensible lifecycle order.
9. **Task `OVERDUE` status is never auto-set** — there's no scheduled job that flips a task to overdue when its due date passes. The Managing Partner Dashboard (`GET /api/tasks/all`, Step 1) works around this by computing an `isOverdue` flag on read (`dueDate` passed and status isn't `COMPLETED`) rather than relying on the stored enum value — the underlying `TaskStatus.OVERDUE` value itself still needs a real trigger (or its own removal in favor of the derived flag everywhere) before Phase 8.
10. **No password-reset / forgot-password flow** for staff or clients.
11. ~~No rate limiting or brute-force protection~~ **Fixed:** `express-rate-limit` on all `/api` routes (300 req/15min) plus a tighter limit on `login/staff`, `login/client`, and `refresh` specifically (10 req/15min), disabled only under `NODE_ENV=test`. Trips are logged via the new security logger.
12. **Client credential delivery is manual** — the temporary password is returned once in the API response for staff to relay by hand; there's no automated secure delivery (that's a Notifications-module feature, Phase 2+). Entropy bumped from 48 to 96 bits as part of Security Hardening, but the manual-delivery process itself is unchanged.
13. **No revoked/expired session cleanup job** — `UserSession`/`ClientSession` rows accumulate indefinitely.
14. ~~No file-type/malware validation on document uploads~~ **Addressed:** MIME + extension allowlist, in-house magic-byte verification (rejects spoofed/renamed files), and a malware-scan integration point (`documents/fileValidation.ts`'s `scanForMalware` — currently a pass-through stub; no AV engine is provisioned yet, that's separate infrastructure work).
15. **Document `confidentiality` flag (INTERNAL vs CLIENT_VISIBLE) is stored but not yet enforced anywhere** — there's no Client Portal yet to enforce it against.
16. **Advocate removal from a case** has a backend endpoint but no UI control yet (only assignment during case creation is wired up in the UI).
17. **Prisma is on 5.x**; a major upgrade (7.x) is available upstream but was intentionally not taken during Phase 1 to avoid destabilizing the build.
18. ~~No AV engine wired to the malware-scan integration point~~ **Partially addressed in Version 1.0 Milestone 4:** EICAR-signature + executable-magic-byte heuristic detection replaces the no-op stub. A full third-party AV engine (ClamAV daemon or a cloud scanning API) remains unprovisioned infrastructure, a further upgrade beyond this.
19. **CSRF:** not mitigated via a dedicated token scheme — reasoned decision, not an oversight. Every state-changing endpoint authenticates via a Bearer token in the `Authorization` header, which a cross-site request cannot forge; the one cookie-authenticated endpoint (`/api/auth/refresh`) uses `SameSite=Lax` by default (configurable to `strict`) as its mitigation. Revisit if any endpoint ever moves to cookie-only auth.
20. **Global input sanitization (trim + null-byte stripping) only covers JSON bodies**, not the text fields inside a multipart/form-data upload (document title/category arrive via `multer`, after the global sanitizer runs) — those still get Zod validation, just not the sanitization pass. Low practical impact, worth closing later.
21. **Recycle Bin has no auto-purge after a retention period** (SRD §27 lists this as optional) — deleted records stay restorable indefinitely until a Managing Partner permanently deletes them. Also, permanently-deleted Document files are removed from disk on a best-effort basis only (no retry queue if the filesystem is unreachable at the moment of deletion).
